## Purpose

This is an itemized inventory of every test file in the repository: what
production code it exercises, how (the testing technique used), and why
that coverage exists (the regression class it guards against). It answers
"what tests do we have and what are they actually for." The test source and
the coverage scripts are authoritative when an entry here becomes stale.

This document is the *what exists*, itemized. It is a snapshot as of
2026-08-05 and will drift as tests are added — update the relevant
section whenever a test file is added, removed, or its purpose changes
materially. It is not auto-generated; treat stale entries as bugs the
same way stale code comments are treated elsewhere in this repo.

**Methodology and confidence**: entries were written from test function
names, the production code each test file targets, and package doc
comments — not from executing every test individually and diffing its
assertions against this table row by row. A sample was verified directly
against source during the `a0360b5` adversarial review and held up, but
any single row is more likely to be stale or imprecise than the tests
themselves; treat a row as correctable, not authoritative, if it
disagrees with the code.

**Numbers:** package percentages below are `go test -cover` statement
coverage under the default build (no `-tags duckdb`), current as of the
tracked `coverage-baseline.json`. Reproduce with
`scripts/coverage-go.sh default` / `scripts/coverage-go.sh duckdb` (Go) or
`npm --prefix frontend run test:coverage` (frontend). The exclusion rationale
is recorded beside `scripts/coverage-exclude-go.txt`.

`scripts/check-coverage-ledger-drift.sh` (2026-08-10; widened 2026-08-11;
run via `make coverage-ledger-drift`, standalone — not in `make verify`,
same DuckDB-toolchain reason as `coverage-ratchet` below) checks that
every package-coverage heading above still matches live `go test -cover`
output — this covers every `internal/*` heading, the root `gopmgr`
package, `scripts`, and `tools/*`, not just `internal/*` as the original
2026-08-10 version did — and that every package in that set with live
coverage has a matching heading at all. Any heading it can't classify
into a known package-coverage, non-package-prose, or externally-tracked
(Frontend, checked by `coverage-frontend.sh` instead) bucket is a hard
failure, not a silent skip. It does not check anything else in this
document: a row's test count, its "How"/"Why" prose, or
`internal/applog`'s per-file claim ("100% of `applog.go`") are still
unverified by any automation and rely on the methodology note above.

`scripts/check-coverage-ledger-current.sh` (widened 2026-08-12, run
inside `make coverage-ledger-current`, which is in `make verify`) checks
that every `*_test.go`/`*.test.ts`/`*.spec.ts`/`*.test.js`/`*.spec.js`
file in the repo is at least mentioned somewhere in this document.
Before 2026-08-12 it only recognized `*_test.go`/`*.test.ts`, narrower
than frontend/vitest.config.ts's actual test-discovery pattern
(`src/**/*.{test,spec}.{ts,js}`) — a `.spec.ts`/`.spec.js`/`.test.js`
file would have been picked up and run by vitest but never checked
against this document at all. That match against vitest's `include` is
maintained by hand, not enforced; widening the vitest pattern further
needs the same update here.

**Technique legend** (used in the "How" column throughout):

| Tag | Meaning |
| --- | --- |
| unit | Direct call into a pure function; no I/O, no fixtures. |
| table-driven | One test function, many input/expected-output cases in a loop or `t.Run` subtests. |
| fixture/golden | Builds a real file/document/DB and asserts on its structure or byte content. |
| fault-injection | Forces an otherwise-unreachable error path — a SQLite `RAISE(ABORT)` trigger, a broken loader/reader, a zeroed entropy source — to prove error propagation. |
| round-trip | Encode then decode (or encrypt/decrypt, wrap/unwrap) and assert the result matches the input. |
| integration | Exercises multiple real collaborators together (e.g. a real `*db.Database` + `*agile.Store` + `Seeder`), not a single function in isolation. |
| e2e | End-to-end: builds a realistic multi-step scenario (an install, a migration, a full export pipeline) and asserts on the final observable outcome. |
| property | Asserts an invariant that must hold across many/all inputs (monotonicity, idempotence, determinism) rather than one fixed expected value. |

## Root package (`gopmgr`, package `main`) — 52.2%

The Wails desktop app entry point, App struct (bound to the frontend via
`window.go.main.App`), and CLI/headless dispatch. Most of this package's
~90 test files are integration tests against a real `*App` wired to a
real (temp-dir) `*users.Store` and `*db.Database` — this package has no
network or GUI dependency to mock, so tests build real state and assert
on real outcomes rather than mocking collaborators.

**Note on this heading's own guarantees**: it is **not** covered by
`check-coverage-ledger-drift.sh` — that script's heading regex only matches
`` ## `internal/...` `` headings, so this one (and any future non-`internal/`
heading) is silently never checked. That's a real gap in the script relative
to its own stated "unparseable heading is a hard failure, not a
pass-by-omission" design principle — confirmed directly by reading the regex,
not assumed. Deferred rather than fixed in this increment (root-package
coverage work, not a `scripts` package change), but disclosed here rather
than left implicit: this 52.2% is hand-verified against `go test ./... -cover`
(the drift script's own invocation, not just `go test .`) as of 2026-08-11,
not drift-script-guarded. A future increment fixing the regex should correct
this number (and any drift that accumulates before then) in the same commit
that changes the regex, since the moment it starts matching, an
already-stale number would fail the script.

Closed via one dedicated test per method plus targeted edge cases, most notably: `TestMoveWorkItem_AwayFromDonePreservesClosedAt`, which locks in a genuinely easy-to-miss asymmetry in `MoveWorkItem`'s SQL — the `CASE WHEN ? = 'done' THEN ? ELSE closed_at END` expression only stamps `closed_at` when the destination is "done"; moving an already-closed item to any other column does NOT clear it. Fault-seeding confirmed a test asserting only "ClosedAt is non-zero" would miss both a re-stamp-on-every-move mutation and a clear-on-leaving-done mutation — the test pins the exact preserved value, not just non-zero-ness. `TestSaveWorkItem_UpsertUpdatesFieldsAndPreservesCreatedAt` is the other timestamp-precision test pinned this way: `created_at` is deliberately absent from the `ON CONFLICT DO UPDATE SET` column list, which is what preserves it across an update; fault-seeded by adding `created_at = excluded.created_at` to that list and confirming the test catches the now-overwritten value — the two saves' independently-computed `now` values differed at nanosecond precision, so the test is a real check, not a coincidence of two saves landing on the same timestamp. `TestDeleteSprint_RemovesSprintAndClearsWorkItemReferences` similarly locks in that deleting a sprint clears `sprint_id` on the work items that referenced it (not just that the sprint row itself is gone) — fault-seeded by removing that `UPDATE` and confirming the test catches the orphaned reference. `TestListWorkItems_ScopesToProjectAndOrdersByOrderIdx` and `TestWIPCountByColumn_ScopesToProject` seed a second `project` row directly via SQL to prove the `WHERE project_id = ?` predicates actually filter — both tests' comments are explicit that this two-project state is not reachable through the application today (`.pmforge` files hold exactly one project each per the schema comment on `internal/db/sqlite.go`'s `project` table), so a future reader doesn't conclude multi-project files are supported. `TestListSprints_OrdersNewestFirst` seeds `created_at` directly via SQL with clearly-separated values rather than through two back-to-back `SaveSprint` calls, since that column is a DB-side `strftime(...)` default with millisecond precision and not settable through `SaveSprint`'s own INSERT column list — two real inserts in the same test could otherwise land in the same millisecond and make the DESC-ordering assertion flaky. `TestStoreMethods_PropagateClosedConnectionErrors` closes the DB and table-drives every remaining method to confirm none silently returns a zero value on a dead connection; its own doc comment discloses that for methods with more than one sequential DB call (e.g. `SaveWorkItem`'s Exec followed by its own `GetWorkItem` call), this proves end-to-end propagation but doesn't pin the specific first guard — fault-seeding `SaveWorkItem`'s own `if err != nil` guard confirmed the closed-DB test stays green regardless (masked by the second call also failing), the same cascading-fallible-path shape documented throughout `internal/users/store_test.go`. `TestEnsureDefaultColumns_PropagatesExecutorError` unit-tests that free function directly against a fake `columnExecutor` rather than trying to force a live transaction's INSERT to fail mid-flight. Four corrupted-column tests (`agile_columns.order_idx`, `agile_work_items.points`, `agile_sprints.capacity`, `agile_deployments.successful` each set to a non-numeric string via SQLite's permissive type affinity) force the `Scan` failure branches in `ListColumns`/`scanWorkItem`/`scanSprint`/`ListDeployments` — same technique as `internal/users`' `is_admin` column corruption. One planned corrupted-column test (`EnsureDefaultBoard`'s existing-default-board Scan-error branch) was abandoned after actually running it and discovering `is_default` is both the only non-string column in that `SELECT` and the column the `WHERE is_default = 1` clause filters on — corrupting it makes the row stop matching the `WHERE` clause before `Scan` ever runs, so it silently takes the `sql.ErrNoRows` seed-a-new-board path instead of erroring; that branch is left to the closed-connection test, which reaches it via a different failure mode ("database is closed" is also `!= sql.ErrNoRows`). Known gaps, left disclosed rather than chased further: `EnsureDefaultBoard`'s transaction-body branches (`tx.Begin`/`tx.Exec`/`tx.Commit`/`ensureDefaultColumns` inside the seed path) and `DeleteSprint`'s two `tx.Exec` calls have no forceable trigger that fails one specific call without failing the ones before it on the same live connection — the same "no hook between two calls on the same live connection" class `internal/users/store.go`'s ledger entry documents; `WIPCountByColumn`'s `rows.Scan` failure on a `COUNT(*)` aggregate has no realistic corruption path since SQLite's own `COUNT()` output is always a valid integer. Separately discovered and deliberately deferred (not fixed this increment): six `Store` methods (`GetWorkItem`, `DeleteWorkItem`, `GetSprint`, `DeleteSprint`, `DeleteColumn`, `DeleteDeployment`) take a bare ID with no `project_id` predicate, unlike this codebase's other project-scoped DAOs. Confirmed inert today, not a live vulnerability: `internal/db/sqlite.go`'s own schema comment states a `.pmforge` file "currently contains exactly ONE project, but the table is shaped to support multi-project files later" — so no cross-project ID can reach these methods through the application as it exists. Recommended trigger for revisiting: add `project_id` predicates to these six methods before multi-project-file support ships, not before. |

## `internal/applog` — 100% of `applog.go` (95.7% of package; `dialog_darwin.go`/`opendir_darwin.go` are platform-narrow and excluded from the ratchet, see `coverage-exclude-go.txt`)

`Init`'s three failure branches (unresolvable log dir, `MkdirAll` failure,

untested because they depend on filesystem failure conditions or on a

`runtime.GOOS` in Phase 1 — so tests can force the "nothing is writable"
path and observe `Fatal`'s behavior without touching the real filesystem,
popping a native dialog, or terminating the test binary.

The twelfth increment's fixed-width TEXT format made ordering correct only as long as every write call site remembered to use `nowTimestamp()` instead of reaching for `time.Now().Format(time.RFC3339Nano)` directly -- nothing in the type system stopped a future call site from doing exactly that. This increment adds a `<col>_unixnano INTEGER NOT NULL DEFAULT 0` sibling column for all 15 `timestampRetrofitTargets` columns and switches every `ORDER BY` (7 sites across `baselines.go`, `charts.go`, `documents.go`, `resource_calendars.go`, and `scenarios.go` ×3) from the TEXT column to its `_unixnano` sibling: numeric comparison cannot be broken by a string-formatting mistake, unlike lexicographic string comparison, no matter what the TEXT column ever contains. `nowTimestamp() string` was replaced by `captureTimestamp() timestampCapture`, which derives both the TEXT and INTEGER forms from one `time.Now()` reading so the pair can never describe two different instants; all 9 write call sites that populate table columns (audit.go's and audit_checkpoints.go's `nowTimestamp()` calls are unchanged, since those values go into JSON payloads that are never `ORDER BY`'d) were updated to bind both fields, including three sites not obvious from a single grep for `nowTimestamp()`: `scenarios.go`'s bulk "deactivate every other active scenario" `UPDATE` (a plain `UPDATE`, not an `INSERT ... ON CONFLICT`) and both of `scenario_charts`' write paths (`BranchScenarioChart`'s `INSERT`, `SaveScenarioChart`'s plain `UPDATE`). The guard script itself was verified against known-bad and known-good fixture lines using the actual `grep` binary a real invocation would use (BSD grep 2.6.0-FreeBSD on this macOS dev machine, reached via `bash script.sh`, not the interactive shell's `ugrep`-backed wrapper function -- confirmed to differ before trusting either) before being wired into `verify`, including the specific case a naive `\b`-based regex could get wrong (`\bcreated_at\b` does NOT falsely match inside `created_at_unixnano`, since `_` is a word character and `\b` requires a transition to a non-word character -- verified empirically, not just reasoned about). An `INTEGER`-only column, replacing the TEXT form entirely, was considered and explicitly rejected: several structs (`documents`, `scenarios`, `charts`, `project`, `stakeholders`) deliberately use a Go `string` field rather than `time.Time` so the Wails JSON bridge can round-trip an unsaved record's empty timestamp without a parse error, and confirmed via a blast-radius scan that the frontend never re-sorts by these fields client-side (its only `.sort()` calls key on `order_idx`) -- so a fix confined to `internal/db`, leaving the JSON wire contract and every frontend call site untouched, fully closes the real defect (SQL `ORDER BY` correctness) without the larger blast radius the alternative would have carried. `TestAllTimestampColumns_TextAndUnixNanoAgree` is the actual enforcement backstop for the whole design (the Go type system cannot force a call site to bind both `.text` and `.unixNano`): it saves through the real `Save*` functions for all 8 tables, including a second save with changed content wherever an update/upsert path exists, then reads back via raw SQL (bypassing every `Save` function) and fails if the TEXT and INTEGER columns ever disagree. A second increment (2026-08-11) closed the gap that increment's own disclosure named: `FromMajorFloat`'s overflow behavior was previously inherited from Go's float64→int64 conversion, documented as implementation-defined once a value no longer fits — observed to saturate to math.MaxInt64/math.MinInt64 on this toolchain/arch, but not guaranteed, and disclosed as "not fixed." Considered (and rejected) returning a zero `Amount` for out-of-range input, matching the existing NaN/Inf guard's contract: traced through the actual call graph and found this would be a *worse* failure mode, not a fix — `Positive()` returns false for zero, so a corrupted budget would silently drop out of `internal/budget`'s `ByCategory` cost rollups, and `ScaleByRatio` returns zero when `amount.MinorUnits == 0`, zeroing EAC with nothing downstream catching it (`evm.go` only pre-guards `EV == 0`, not `BAC == 0`). A corrupted import would become $0 that reads as legitimate data — worse than the existing $92-quadrillion saturated value, which is at least obviously broken to a human reader. Fixed instead by clamping explicitly to math.MaxInt64/math.MinInt64 by sign in Go code rather than relying on the implementation-defined conversion. Verified by probe on this development machine (arm64/darwin): `1e18`→MaxInt64, `-1e18`→MinInt64, identical before and after — a no-op there, since arm64's FCVTZS already saturates toward the input's sign. **Not a no-op on amd64 (this repo's CI target)**: the prior test comment documents amd64 historically producing a single sign-losing "integer indefinite" value for either direction, so the explicit clamp is a real, strictly-more-correct behavior change there (sign-losing indefinite value → sign-preserving saturation), not independently re-verified on amd64 this increment — the claim rests on that prior documented finding. Converts an inherited, architecture-dependent toolchain artifact into a guarantee of the function itself on every architecture. `Add`/`Sub` still have no overflow protection of their own (`a.MinorUnits + b.MinorUnits` can wrap silently) — noted as a follow-up candidate, not addressed this increment, since it's a different guard at a different boundary and the package's existing posture doesn't otherwise protect arithmetic overflow.
