## Purpose

This is an itemized inventory of every test file in the repository: what
production code it exercises, how (the testing technique used), and why
that coverage exists (the regression class it guards against). It answers
"what tests do we have and what are they actually for." The test source and
the coverage scripts are authoritative when an entry here becomes stale.

This document is the *what exists*, itemized. It is a snapshot as of
2026-08-05 and will drift as tests are added — update the relevant
section whenever a test file is added, removed, or its purpose changes
materially. It is not auto-generated; treat stale entries as bugs the
same way stale code comments are treated elsewhere in this repo.

**Methodology and confidence**: entries were written from test function
names, the production code each test file targets, and package doc
comments — not from executing every test individually and diffing its
assertions against this table row by row. A sample was verified directly
against source at commit `a0360b5` and held up, but any single row is
more likely to be stale or imprecise than the tests themselves; treat a
row as correctable, not authoritative, if it disagrees with the code.

**Numbers:** package percentages below are `go test -cover` statement
coverage under the default build (no `-tags duckdb`), current as of the
tracked `coverage-baseline.json`. Reproduce with
`scripts/coverage-go.sh default` / `scripts/coverage-go.sh duckdb` (Go) or
`npm --prefix frontend run test:coverage` (frontend). The exclusion rationale
is recorded beside `scripts/coverage-exclude-go.txt`.

`scripts/check-coverage-ledger-drift.sh` (2026-08-10; widened 2026-08-11;
run via `make coverage-ledger-drift`, standalone — not in `make verify`,
same DuckDB-toolchain reason as `coverage-ratchet` below) checks that
every package-coverage heading above still matches live `go test -cover`
output — this covers every `internal/*` heading, the root `gopmgr`
package, `scripts`, and `tools/*`, not just `internal/*` as the original
2026-08-10 version did — and that every package in that set with live
coverage has a matching heading at all. Any heading it can't classify
into a known package-coverage, non-package-prose, or externally-tracked
(Frontend, checked by `coverage-frontend.sh` instead) bucket is a hard
failure, not a silent skip. It does not check anything else in this
document: a row's test count, its "How"/"Why" prose, or
`internal/applog`'s per-file claim ("100% of `applog.go`") are still
unverified by any automation and rely on the methodology note above.

`scripts/check-coverage-ledger-current.sh` (widened 2026-08-12, run
inside `make coverage-ledger-current`, which is in `make verify`) checks
that every `*_test.go`/`*.test.ts`/`*.spec.ts`/`*.test.js`/`*.spec.js`
file in the repo is at least mentioned somewhere in this document.
Before 2026-08-12 it only recognized `*_test.go`/`*.test.ts`, narrower
than frontend/vitest.config.ts's actual test-discovery pattern
(`src/**/*.{test,spec}.{ts,js}`) — a `.spec.ts`/`.spec.js`/`.test.js`
file would have been picked up and run by vitest but never checked
against this document at all. That match against vitest's `include` is
maintained by hand, not enforced; widening the vitest pattern further
needs the same update here.

**Technique legend** (used in the "How" column throughout):

| Tag | Meaning |
| --- | --- |
| unit | Direct call into a pure function; no I/O, no fixtures. |
| table-driven | One test function, many input/expected-output cases in a loop or `t.Run` subtests. |
| fixture/golden | Builds a real file/document/DB and asserts on its structure or byte content. |
| fault-injection | Forces an otherwise-unreachable error path — a SQLite `RAISE(ABORT)` trigger, a broken loader/reader, a zeroed entropy source — to prove error propagation. |
| round-trip | Encode then decode (or encrypt/decrypt, wrap/unwrap) and assert the result matches the input. |
| integration | Exercises multiple real collaborators together (e.g. a real `*db.Database` + `*agile.Store` + `Seeder`), not a single function in isolation. |
| e2e | End-to-end: builds a realistic multi-step scenario (an install, a migration, a full export pipeline) and asserts on the final observable outcome. |
| property | Asserts an invariant that must hold across many/all inputs (monotonicity, idempotence, determinism) rather than one fixed expected value. |

## Root package (`gopmgr`, package `main`) — 62.4%

The Wails desktop app entry point, App struct (bound to the frontend via
`window.go.main.App`), and CLI/headless dispatch. Most of this package's
~90 test files are integration tests against a real `*App` wired to a
real (temp-dir) `*users.Store` and `*db.Database` — this package has no
network or GUI dependency to mock, so tests build real state and assert
on real outcomes rather than mocking collaborators.

**Note on this heading's own guarantees**: `check-coverage-ledger-drift.sh`
only matches `` ## `internal/...` `` headings, so this one (and any future
non-`internal/` heading) is silently never checked — a real gap relative to
the script's own "unparseable heading is a hard failure, not a
pass-by-omission" design, confirmed by reading the regex rather than
assumed. This 52.2% is hand-verified against `go test ./... -cover` as of
2026-08-11 but not drift-script-guarded; a future fix to the regex should
correct this number in the same commit, since a stale number would then
start failing the check.

**The RFC3339Nano timestamp-ordering hazard and its fix** — the most
significant finding in this package. `documents_read_test.go` first
named a real, verified ordering bug: `ORDER BY updated_at DESC` sorts
stored RFC3339Nano *strings* lexicographically, and Go's RFC3339Nano
formatting omits the fractional-seconds component entirely when it's
exactly zero — so a document saved at an exact whole-second boundary can
sort lexicographically *after* one saved with any positive fraction in
the same second, backwards from chronological order (confirmed directly
with `time.Format`). The same hazard was found to affect `charts.go`'s
`ListCharts` (whose doc comment incorrectly claimed the ordering "stays
chronological," corrected alongside the fix), `baselines.go`, three
queries in `scenarios.go`, and `resource_calendars.go` as a
lower-priority tertiary tiebreaker. `sigma_projects.updated_at` was
initially thought to share the risk but does not: that column is
populated via SQLite's own `strftime` default, which always emits a
fixed 3-digit fraction, unlike the Go trimming format the hazard
actually requires — corrected once this was checked directly.

The hazard was fixed in two stages. First, a `nowTimestamp()` helper
using a fixed-width RFC3339 layout (always exactly nine fraction digits,
verified to close not just the documented whole-second case but the
general case where any two same-second timestamps with different
trimmed-fraction widths can invert lexicographic order) replaced the
trimming format at all 11 Go write call sites; a migration normalizes
every pre-existing on-disk value across 15 columns in 8 tables to the
fixed-width format on every database open. `audit_events.timestamp_utc`
is deliberately excluded from this retrofit (though its write site was
still switched to `nowTimestamp()` going forward): it's one of the
fields `eventHash` hashes, so rewriting an already-hashed value would
break `VerifyAuditChain`'s tamper-evident chain for every database with
existing audit history, and it's never used in an `ORDER BY`, so
retrofitting it would have bought only cosmetic consistency at the cost
of a real compliance guarantee — proven by a test that seeds a
legacy-format value into that column and confirms the retrofit leaves it
byte-for-byte untouched, paired with an end-to-end test confirming
`VerifyAuditChain` still passes after the retrofit runs.

Second, at the user's explicit request for "the best close to
unbreakable structure," the convention-based TEXT fix (which depended on
every future write call site remembering to use `nowTimestamp()` rather
than reaching for `time.Now().Format(time.RFC3339Nano)` directly) was
replaced with a structural one: a `<col>_unixnano INTEGER` sibling
column was added for all 15 target columns, and every `ORDER BY` (7
sites) now sorts on the integer column instead of the TEXT one —
numeric comparison can't be broken by a string-formatting mistake the
way lexicographic comparison can. `nowTimestamp() string` was replaced
by `captureTimestamp() timestampCapture`, which derives both the TEXT
and INTEGER forms from one `time.Now()` reading so the pair can never
describe two different instants; 9 write call sites were updated to
bind both fields, including three non-obvious ones found only by
careful review, not a single grep for the old helper name. Two existing
indexes were repointed to the new integer columns by a migration step
that validates the on-disk column set before dropping anything (failing
loudly rather than silently narrowing the index if the schema ever
changes without updating that check) and wraps the drop+create in one
transaction so a crash between the two statements can't permanently
leave the index missing — an earlier version of this migration step
treated an empty observed column set as "nothing to do" rather than
"must recreate," a real bug caught and fixed before it was ever
committed. An `INTEGER`-only column, replacing the TEXT form entirely,
was considered and rejected: several structs deliberately use a Go
`string` field so the Wails JSON bridge can round-trip an unsaved
record's empty timestamp without a parse error, and a check confirmed
the frontend never re-sorts by these fields client-side — so a fix
confined to `internal/db` fully closes the SQL-level defect without
touching the JSON wire contract.

`sigma_projects.updated_at`'s exemption from the retrofit is now backed
by an inline marker comment and a CI guard script
(`scripts/check-no-text-timestamp-ordering.sh`, wired into `make
verify`) that fails the build on any future `ORDER BY` against a bare
TEXT timestamp column without that marker; its safety claim was verified
by reading SQLite's own `strftime` format specification, and the guard
script's regex was verified against the actual `grep` binary a real
invocation would use, including the specific case a naive
word-boundary regex could get wrong (`created_at` doesn't falsely match
inside `created_at_unixnano`, since `_` is a word character).

`TestAllTimestampColumns_TextAndUnixNanoAgree` is the actual enforcement
backstop for the whole design, since the type system can't force a call
site to bind both halves of a `captureTimestamp()` pair: it saves
through the real `Save*` functions for all 8 tables, then reads back via
raw SQL and fails if the TEXT and INTEGER columns ever disagree.
Building this test surfaced a real gap in the test itself during
fault-seeding, not the implementation: an early version checked the
wrong scenario row after seeding a bug in the bulk-deactivation
`UPDATE`, because the row it checked had never actually been touched by
that statement — caught and corrected to check a row the deactivation
actually reaches. `explainUsesIndex` measures, via `EXPLAIN QUERY PLAN`,
that the two repointed indexes still serve their queries' sorts — one
query was found to still require a full temp-B-tree sort regardless of
which timestamp column it targets, since its leading sort key was never
part of the index either before or after this fix, a pre-existing
characteristic rather than a regression.

**Shared `truncDoc` fix.** The byte-vs-rune truncation defect found in `truncTC` turned out to be
duplicated, byte-for-byte, across eight more per-renderer files — `truncC` (communication_plan.go),
`truncClo` (closure.go), `truncExec` (execution_plan.go), `truncProc` (procurement_plan.go), `truncIssue`
(issue_log.go), `truncBudget` (project_budget.go), `truncReq` (requirements.go), `truncR` (risk_register.go)
— all with zero test coverage. Fixed by extracting one shared `truncDoc(s string, n int) string` in
`charter.go` and turning each of the nine `trunc*` functions into a one-line wrapper delegating to it (kept
as named wrappers, rather than rewriting ~30 call sites, to avoid a large diff and keep existing test names
valid).

The first implementation attempt switched `n`'s meaning from a byte budget to a rune-count budget, which
fixes UTF-8 validity but breaks layout: measured against a real column (`issue_log.go`'s 75mm-wide
Description field, `truncIssue(it.Description, 64)`) with the app's real embedded font, the rune-count
version rendered at 133.6mm — overflowing the column by nearly 2× — versus 46.5mm under the old byte-based
code. That's a real risk for any project with non-Latin content, not a theoretical edge case. The shipped
design keeps `n` as a byte budget and adds only a rune-boundary back-off (`cut := n-1`, then walk left while
`!utf8.RuneStart(s[cut])`), so a multi-byte character that doesn't fully fit is dropped whole instead of
split. This provably never produces more bytes than the old code for the same input (by inspection: `cut`
only moves left from `n-1`, where the old code always cut), so rendered width can only shrink or stay equal
everywhere — confirmed at the same real column (46.5mm both ways). For ASCII input the back-off loop never
executes, so output is byte-for-byte identical to the old implementations. A side effect of the redesign:
`n <= 0` no longer panics (degrades to a bare `"…"`), unlike every old implementation, which panicked on a
negative slice index; not relied on by any real call site (all use positive literals, 16–120) but verified
directly.

Before implementing, checked whether the dangling-lead-byte defect could cause an actual panic (not just a
cosmetic glyph) on the app's real embedded-font PDF path (fpdf's `utf8toutf16`, reached only when a TrueType
font is registered via `SetFontApplier` — `go test` normally uses core Helvetica, which sidesteps this).
Built a real `*fpdf.Fpdf` with `AddUTF8FontFromBytes` against the app's actual embedded font and fed it the
historical buggy output plus a sweep of truncation offsets: no panic in any case, because the old `trunc*`
functions always appended a 3-byte ellipsis whose bytes happened to satisfy `utf8toutf16`'s greedy
continuation-byte reads (mis-decoding, not an out-of-bounds read). That check doesn't cover `truncDoc`'s
passthrough branch (`len(s) <= n` returns `s` unmodified), so the input path was traced instead: every
string this package sees originates from `renderRaw`'s `json.Unmarshal`, and `encoding/json` was confirmed
to always substitute U+FFFD (valid UTF-8) for invalid byte sequences on decode — so `s` is guaranteed valid
UTF-8 at every real call site.
