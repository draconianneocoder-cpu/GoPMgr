## 1. Scope and effect of the acceptance

The maintainer **accepts the architectural direction in ADR-010 v2.2, including D-01–D-19 and QI-01–QI-15, subject to the binding interpretations and evidence reservations recorded below.** These requirements become the approved *target design*. Acceptance does not establish that implementations, dependencies, platform transports, physical durability, legal obligations, or performance claims have been demonstrated.

Nothing else follows automatically from this record.

No production worker, G1-onward feature work, new database format, SQLCipher migration, altered encryption/key access, project publication pipeline, AI integration, signed release, new external dependency in production, or relaxation of cross-platform and fidelity requirements is authorized without its own satisfied prerequisites and maintainer authorization. ### Interpretive safeguards binding on OWN-01–OWN-11

- **Feature and platform fidelity:** No switch to TCP, custom stdio framing, single-language/MPXJ-specific plugin APIs, omitted source entities, full-document frontend rendering or automatic merge merely for expedience.
- **Data authority:** The Go host alone owns authenticated sessions, keys, SQLCipher, schedule authority, exact money, revisions, audit and publication. A bundled worker is trusted code, **not** an OS sandbox.
- **Evidence durability:** Retained source evidence, encrypted field reports, audit references and import receipts must be sealed inside the published project boundary, verified on readback, included in supported backup/restore flows, and must never be deleted by staging cleanup. If original source bytes were explicitly not retained, the receipt must state that limitation.
- **Proven results:** A working Go pipe/listener, operating-system AF_UNIX support, or a nominal MPXJ format capability does not prove Java gRPC end-to-end behavior, import completeness or a successful packaged release.
- **Scope:** A blocked platform is **BLOCKED**, not silently unsupported in the accepted design; any proposed change in advertised target coverage or architecture requires an ACR.

## 3. Final answers to integration review §4 (INT-01–INT-04)

### INT-01 — Journal integrity: **APPROVED; authenticate, do not claim an unspecified signature**

**Decision.** The durable import intent journal and sealed-project manifest must be cryptographically authenticated and verified before recovery can authorize publication. Replace ambiguous phrases such as *signed journal* with **HMAC-authenticated intent journal**, subject to a documented domain-separated, purpose-specific key design. This is a requirement, **not** approval of an unreviewed KDF, exact key source or persistent key-storage arrangement.

**Binding requirements:**

1. Authenticate a canonical versioned journal encoding containing operation ID, account/principal incarnation, intended project identity, candidate and seal digests, source/evidence manifest reference, journal state and final target when chosen.
2. Select an approved key derivation and lifecycle compatible with GoPMgr's DEK rewrap, recovery-code, password reset, administrator escrow and deletion semantics. Do not use an ephemeral session-only key that prevents legitimate recovery after restart; do not store a usable MAC key in the journal.
3. Keep writes durable using atomic replacement/creation, appropriate file and directory sync, and a journal state machine with an independently validated physical-state comparison. Implement replay/double-publication protection and idempotent reconciliation.
4. **Do not mistake a valid MAC for freshness.** A previously valid but rolled-back journal can still pass an HMAC. Detect or safely handle rollback/inconsistency using an authoritative operation/receipt marker, physical state, sealed digests and monotonic/reconciliation checks; specify the guarantee honestly.
5. An invalid/missing/unverifiable journal must not authorize a fresh publication or cause destructive cleanup. Safely quarantine operation-owned staged material for authenticated review; never sweep normal legacy `projects/` folders based on the absence of ADR-010 journals.
6. Add tamper, rollback, key-rotation/rewrap, wrong-user, interrupted-fsync, missing-seal, replay and crash-state tests. Update `PUB-007` and the publication recovery matrix.

**Reserved:** The exact MAC algorithm/KDF/secret boundary and anti-rollback state design are to be proposed in a security-reviewed G3 publication contract/ADR-011 dependency and separately accepted before implementation. If infeasible, file an ACR; do not weaken the authentication requirement.

### INT-02 — Bootstrap: **APPROVED AS A G0-CANDIDATE, NOT A BUSINESS-DATA TRANSPORT**

**Decision.** A parent-owned, inherited, private **one-shot stdin pipe** is approved for G0 prototyping to convey an unpredictable single-use bootstrap credential and bounded endpoint metadata to the Java child. Business-data RPCs must still use generated gRPC/HTTP/2 services over the G0-proven local OS IPC endpoint.

**Binding requirements:** length-bounded, versioned one-shot bootstrap; no source/project records via stdio; no credential in argv, persistent environment, logs, traces or crash reports; validated process parentage and launch identity; expiration/replay resistance; host-created restricted endpoint, verified caller authorization and connection binding; pipe closure and process-tree cleanup. Prove Windows/macOS/Linux behavior and hostile-child/replay/squat tests. A safer portable alternative may be proposed without replacing the gRPC business contract.

**Reserved:** Final platform-specific bootstrap implementation and whether extra OS-credential proof is available are G0 acceptance matters. No unproven transport is thereby approved for production.

### INT-03 — Sync-managed paths: **APPROVED — SUPPORT POLICY MUST BE EVIDENCE-BASED AND NONDESTRUCTIVE**

**Decision.** Do not declare live SQLCipher/SQLite/WAL storage safe on unvalidated cloud-sync-managed or network filesystems. Prefer durable local application-data paths for **new installations** after an approved cross-platform location and migration design; preserve existing project access and never silently relocate or delete user data.

**Binding requirements:**

1. Current versions place some project roots under `~/Documents`; treat existing locations as compatibility inputs, not as mistakes to overwrite automatically.
2. For new and existing paths, define tested supported filesystem properties: locking, same-volume no-replace rename, WAL/checkpoint behavior, case/path/ACL behavior, durability and recovery. SQLite WAL is not supported for clients on different machines sharing a network filesystem; a synchronized local directory presents *additional* race/copy hazards requiring separate tests.
3. Do not claim perfect detection of OneDrive, Dropbox or other sync clients. Test representative redirection and sync scenarios; warn or block **new publication** only under a specific approved supported-location policy, with actionable relocation/backup guidance.
4. Any change to default storage roots requires a separate non-destructive migration/upgrade UX and consent/rollback plan, not an incidental G3 path refactor. Backup/export to an intentional sync target can remain supported without treating it as live project storage.
5. Do not automatically block legacy project reads or repair/restore paths based on a heuristic warning. Distinguish unsupported **new writes/publication** from best-effort access to existing data, while protecting against known corruption conditions.

**Reserved:** Exact default paths and which sync-managed configurations qualify as supported remain for platform testing and a separate accepted migration/location decision.

## 4. Quality-assurance corrections adopted with this acceptance

The earlier *recommended* record was sound but not sufficiently precise in five areas. This accepted replacement tightens them without reversing user intent:

| Issue in earlier record | Accepted refinement |
|---|---|
| Journal HMAC might be read as an already-reviewed cryptographic implementation | Bind authentication and tests, but defer exact key derivation, DEK/escrow rotation handling and anti-rollback construction to security review. |
| “Windows named-pipe gRPC approved” could be read as tested interoperability | This approves the target **only**; Windows named pipes and AF_UNIX remain experimental until a real Go↔Java gRPC gate passes. |
| An unsupported cloud-sync root could be interpreted as warrant for blanket project rejection or silent relocation | Adopt a measured filesystem support policy, preserving legacy access and requiring a separate migration decision. |
| Conditional dependency approval could be mistaken for G1 production authorization | Authorize isolated G0 prototypes now; no production dependency changes without separate phase approval. |
| “Accept v2.2” could be conflated with test PASS or implementation | Accept QI/D architecture while keeping all untested implementation and release gates open. |

Additional consistency requirement: update relevant test captions, status history, source-proof references and the `OWN-` register. No test oracle or requirement may be weakened merely to reflect this decision.

## 6. Source hierarchy and verification limits

This record expresses maintainer **approval of architecture**, not a verified fact about deployed software. The uploaded ADR and plan establish intended design. The agent's `integration-review.md` states its assessment of code and upstream evidence; those claims still require rechecking against the actual implementation HEAD before changes. Useful primary references for implementation verification:

- SQLite WAL: <https://www.sqlite.org/wal.html> — shared-memory/network-filesystem limitations, checkpoint behavior.
- SQLite atomic commit: <https://www.sqlite.org/atomiccommit.html> — durability depends on filesystem and sync semantics.

- OpenJDK AF_UNIX design: <https://openjdk.org/jeps/380> — JDK socket capability alone is not grpc-java compatibility evidence.
