## 2. Architectural direction and evaluated alternatives

| Question | Long-term high-quality choice | Rejected/qualified alternative and reason |
|---|---|---|
| Integration language | Go owns core; Java MPXJ isolated; Rust and other languages possible later | Rewriting MPXJ requires extensive parser maintenance; JNI risks main-process stability |
| Worker protocol | Standard **gRPC with typed protobuf** over local OS IPC | Custom stdio protobuf not acceptable as main protocol; manual multiplex, cancellation and backpressure costs |
| Linux/macOS transport | Private authenticated UDS with real Go↔Java grpc transport | Loopback listener unnecessary when UDS viable |
| Windows transport | Host-created named pipe with proven Java grpc client over HTTP/2; AF_UNIX as measured alternative | Go-winio server success does **not** prove grpc-java named-pipe support; no silent stdio/TCP switch |
| Supervisor | Small Go-owned lifecycle manager with internal capability registry | Mandatory HashiCorp go-plugin has transport constraints; defer public SDK/marketplace, not internal modularity |
| Operation lifetime | One subprocess per job initially; pooled workers only after measured need and reauth proof | Always-persistent JVM retains project/session state and complicates isolation |
| Identity | Artifact digest, logical lineage, producer-scoped entity keys plus append-only mapping evidence | Names, paths, hashes or reused UIDs alone do not identify same logical task |
| Data fidelity | Independent presence, conversion, representation, edit, export and validation properties | One disposition enum cannot express exact-and-readonly and opaque-but-preserved at once |
| Publication | Encrypted, complete project-owned candidate **including retained evidence**, sealed then atomically no-replace renamed | Separate staging evidence folder deleted after rename causes source loss |
| Legacy/recovery | Journal only for interop staging; fresh authorization for future publication; idempotent reconciliation | Quarantine without journal across `projects/` risks legitimate data; expired session approval unsafe |
| Persistence | Approved ADR-011 normalized typed tables + one write authority; existing WBS independent | Raising row constants/keeping whole chart JSON as editable master cannot satisfy scale |
| Audit | Mixed legacy chain verifiable; typed delta/evidence digests; separately retained receipts/undo | Rehashing old audit or storing entire schedule before/after per edit is unsafe/expensive |
| Analytics | Deterministic GoPMgr kernel + domain-query APIs; accelerator behind benchmarked adapters | DataFusion/Arrow/Iceberg do not replace transactional per-user SQLCipher storage by themselves |
| AI | Optional MCP/provider adapters with revocable scoped grants; human-approved diffs | Model-generated calculations or autonomous edits must not be authoritative |
| Security | OS endpoint permissions + launch auth + resource caps, truthful same-user process threat model | Separate process ≠ OS sandbox; tests observing no network ≠ network denied |
| Compliance | Signed distributed bundle plus legally reviewed LGPL replacement mechanism | Absolute immutable digest lock with no replacement route may conflict with user replacement rights |

## 4. Source verification and disputed facts

- `internal/export/mspdi_import.go` chart importer skips summary rows and assumes eight-hour working days; it is deliberately retained as a limited legacy **Quick chart import** but not claimed as complete project import.
- `internal/analytics/duckdb.go`: `maxImportRows=10000` caps materialized result rows; not overall on-disk schedule capacity.
- `internal/wbs/model.go`: `MaxPayloadBytes=8<<20`, `MaxNodes=10_000`; these constrain the current WBS aggregate, independent of schedule task volume.
- `internal/db/charts.go` and `internal/db/wbs_store.go` write full before/after chart JSON into audit events; a future normalized change API must preserve historical audit proofs.
- Existing GoPMgr currently packages SQLCipher/SQLite 3.33.0; features such as modern STRICT schema, `RETURNING`, newer JSON functions and optional FTS need a separate reviewed upgrade/build decision.
- Existing project discovery uses folder scan; there is no reason to invent a mandatory catalog registration transaction for today's new-project publication. Any future catalog requires a separate coordinated design.
- The agent's reference to `ProjectLibreReader` is a **candidate**. Supported POD producer versions and complete data coverage require actual fixtures; "a library recognizes a file" is not feature parity.
- MPXJ native `.mpp` writing must not be claimed; export directions are per-format, per-version and test-gated.
- A plain Go Windows named-pipe listener does not prove Java can speak HTTP/2 gRPC over it. Microsoft .NET named-pipe gRPC documentation also does not prove grpc-java support. Native UDS is well established at OS level on POSIX, but Java Netty transport and bundled native classifiers still need installed testing.

## 5. Residual high-impact design risks

| Risk | Likelihood assessment | Impact | Decision or proof needed |
|---|---|---|---|
| Windows Java named-pipe client transport unavailable/fragile | Material unknown | Blocks Windows MPXJ plugin | G0 prototype, compare AF_UNIX; owner exception ACR only |
| Long-term LGPL / signed-bundle replacement tension | Material legal uncertainty | Distribution blocker | Real legal review with signed alternate-library workflow |
| Worker executing as same user reads other accessible files | Known threat-model limitation | Confidentiality | Bundled-only trust; future OS sandbox for third parties |
| SQLCipher old-format downgrade | Known pre-gate risk | Corruption | Gate release, history version matrix, backup/warnings |
| Project evidence doubles storage | Data-dependent | Disk and backup performance | Encrypted chunk retention policy + measured compression/dedupe |
| MPXJ unable to expose some proprietary fields | Format-dependent | Parity caveats | Reader matrix + opaque original + user-visible unknowns |
| Incremental CPM not equivalent to full scheduling | Algorithmic risk | Wrong schedule | Differential tests; full recompute fallback |
| A huge data model gets reserialized for Wails | High without API boundary | UX/memory crash | Paged query and viewport contract from S3/S5 |
| Package signing native Netty/JDBC libraries | OS-dependent | Installer release failure | Real notarization/Windows signature gates |
| Audit evidence GC destroys proof | Design-dependent | Forensics | Immutable digests and retention/replay tests |

## 6. Changes intentionally *not* made

1. No promise of immediate full format/version parity or native MPP export.
2. No assumption MPXJ parses every field or can infer unknown attributes.
3. No automatic WBS v2 enlargement; WBS scope remains separate.
4. No use of Apache Iceberg/DataFusion/Arrow as a drop-in primary OLTP database.
5. No removal of SQLCipher, existing recovery, administrator escrow, audit or established Wails release requirements.
6. No mandatory cloud service, subscription or model-provider integration.
7. No third-party plugin marketplace/public SDK in the first production slice.
8. No silent TCP/stdio fallback when Windows Java local gRPC is unproved.
9. No fake p95, no invented bench data or claimed testing based on a written plan.
